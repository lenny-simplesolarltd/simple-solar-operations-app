This matters more than anything else in this report: the semantics differ between them, and only the later two ever touched the cloud.

## 1. Command envelope, validation, registry, dispatch

### 1.1 G1 envelope (`R/processor/types.js:91-107`, `R/processor/command.js:6-16`)

Fields produced by `makeCommand`: `command_id` (`'CMD-'+base36 ts+'-'+random`), `source:'appsheet'`, `actor_email`, `actor_roles[]`, `entity_type` (hard-coded `'Job'`), `entity_id`, `expected_version` (`|| null`), `command_type`, `payload` (frozen copy), `submitted_at` (ISO), `payload_hash` (32-bit string hash `simpleHash`, `types.js:109-117`).

`validateCommandEnvelope` requires: object; string `command_id`; string `command_type`; string `entity_id`; truthy `submitted_at`; truthy `payload_hash`; string `actor_email`; array `actor_roles`. `expected_version` and `payload` are NOT required. `validatePayload` (`command.js:38-58`) checks required/typed fields only if a `commandSchema` was injected; none is shipped — returns valid when schema absent (line 39).

Registry: `CommandType` enum of 16 (`types.js:4-21`): COMPLETE_TASK, RECORD_CALL, RAISE_ISSUE, MOVE_JOB, CHANGE_INSTALLER, CANCEL_JOB, APPROVE_OPERATIONAL_COMPLETE, CREATE_ORDER, RECEIVE_DELIVERY, STOCK_MOVEMENT, SUBMIT_COMMISSIONING, REVIEW_COMMISSIONING, SEND_COMMUNICATION, RECONCILE, HEALTH_CHECK, PROCESS_INTAKE.

**There are no handlers in G1.** `computeChanges` copies the whole payload onto the entity (`processor.js:239-248`) and `applyChanges` upserts it (`:250-278`). The only command-specific behaviour: APPROVE_OPERATIONAL_COMPLETE creates a `FIN03` task (`:283-294`); SEND_COMMUNICATION enqueues an EMAIL outbox item (`:302-307`). Unknown command types fall through to `FN-01` (`:236`). `processCommand(null)` throws before the try block (`:56-57`, noted `S04-readiness.md:38`). Not worth porting as logic.

G1 pipeline order (`processor.js:69-215`): envelope → idempotency → resolve actor → permission → payload schema → release mode/pilot scope → acquire lock → version check → prepare journal → mark applying → apply → tasks → outbox → audit → mark committed → record processed command → release lock.

### 1.2 G2 envelope (`R/s04/processor.js:19-30`)

Strict allow-list; any extra key → `INVALID_FIELDS`:
`{command_id, action, task_id, expected_version, payload, payload_hash}`.
- `command_id`, `task_id`: string matching `^[A-Za-z0-9][A-Za-z0-9_-]{0,119}$` else `INVALID_COMMAND_ID` / `INVALID_TASK_ID`.
- `action` must equal `'COMPLETE_TASK'` else `ACTION_DENIED`.
- `expected_version`: safe integer ≥ 1 else `INVALID_VERSION` (**mandatory**).
- `payload` keys ⊆ `{completion_note}`; note must be a string ≤ 2000 chars else `INVALID_PAYLOAD`.
- `payload_hash` is accepted but **dropped** from the normalised request (line 28-29) — the client hash is ignored (`S04-implementation.md:38`).
- No actor fields are permitted in the envelope; `actor_email`/`role` injection → `INVALID_FIELDS` (tests `R/tests/s04.test.cjs:83-84`).

G2 pipeline (`s04/processor.js:102-191`, summarised `S04-implementation.md:19`):
environment guard → strict parse → trusted identity → active People/PersonRoles → **acquire lock** → re-guard → **re-resolve actor under lock** → **re-read task under lock** → permission rules → mode/pilot/synthetic gates → canonical hash + durable idempotency lookup → unresolved-journal check → version + completability → persist Prepared plan → Applying → task update → TaskEvent insert → AuditEvent insert → Committed+result in one row write → release lock.

Note the deliberate ordering: idempotency lookup happens **before** stale-version/state rejection (so a replay of an already-completed command returns the original result) but **after** current permission/mode/pilot checks (a revoked actor or disabled function cannot retrieve results by replay) — `S04-implementation.md:21`, code `:116-145`.

### 1.3 G3 envelope (`R/r1-appsheet/adapter.js:168-222`)

Allowed top-level keys (else `R1A_INVALID_FIELDS`, `:169`):
`command_id, command_type, job_id, task_id, issue_id, work_package_id, old_allocation_id, expected_version, payload`.
- `command_id` non-blank (`R1A_COMMAND_ID_REQUIRED`, `:170`); services further restrict to `^[A-Za-z0-9][A-Za-z0-9_-]{0,80}$` (`services.js:816`, `R1A_INVALID_COMMAND_ID`); the operations contract uses `^[A-Za-z0-9_-]{1,128}$` (`operations-contract.js:155`).
- `command_type` ∈ `R1A_BOUND_COMMANDS` (28 values, `adapter.js:6`) else `R1A_UNKNOWN_COMMAND`.
- Payload per command is allow-listed with required keys by `_r1sPayload(request, allowed, required)` (`services.js:6`): unknown key → `R1A_INVALID_FIELDS`; missing/blank required key `k` → `R1A_REQUIRED_<K>`.
- No actor in the envelope. The actor comes from `options.actorEmail()` (`adapter.js:35`).

Registry/dispatch:
- `R1A_BOUND_COMMANDS` (`adapter.js:6`): COMMISSIONING_RECORD, TASK_COMPLETE, TASK_REOPEN, TASK_EVIDENCE_ATTACH, CALL_RECORD, ISSUE_UPDATE, ISSUE_CREATE, PLANNER_UPDATE, MOVE_JOB, CHANGE_INSTALLER, CANCEL_JOB, REINSTATE_JOB, DEPOSIT_CONFIRM, OPERATIONAL_COMPLETE, BOOKING_GATES, CONFIRM_BOOKING, SOLD_INTAKE, BOOKING_INTAKE, IW_START, IW_PROGRESS, IW_REPORT_COMPLETION, IW_REPORT_PROBLEM, IW_REPORT_VARIATION, IW_COMMISSIONING_DRAFT, IW_COMMISSIONING_SUBMIT, COMMISSIONING_REVIEW, GOODS_IN_RECEIVE, STOCK_QUARANTINE.
- Office commands: handler map `_r1sServices()` (`services.js:1712`) keyed by command_type; adapter calls `service({request, actor, store, resolveUpload})` (`adapter.js:220`). Missing handler → `R1A_COMMAND_UNSUPPORTED` (`:175`).
- `IW_*`, COMMISSIONING_REVIEW, GOODS_IN_RECEIVE, STOCK_QUARANTINE are routed to `_r1cExecute` (`adapter.js:172`), driven by the declarative table `R1C_COMMANDS` (`operations-contract.js:5-16`): `{fields:[allowed payload keys], target:<table whose version is checked>, fn:<backend function name>}`. This declarative shape (allowed fields + version-target entity + handler) is a good model for the new registry.
- Reads are a parallel registry `R1A_BOUND_READS` (18) (`adapter.js:5`), same actor resolution, no mode check for most.

Successful command response shape: `{ok:true, command_type, actor_id, result:{…}}` (`adapter.js:221`). Errors are thrown `Error` with `.code`; the entry point converts to `{ok:false, error:<code>}` (`cloud-adapter.js:8`).

## 2. Actor identity and authorization

### 2.1 Actor resolution

**Business rule (G2 `s04/processor.js:39-47`, G3 `adapter.js:16-25` — identical semantics):**
1. An authenticated email is required (`TRUSTED_IDENTITY_REQUIRED` / `R1A_AUTHENTICATED_EMAIL_REQUIRED`).
2. Normalise: trim + lower-case. Match against `People.email` normalised the same way.
3. Exactly one match required; zero or >1 → `UNKNOWN_OR_DUPLICATE_ACTOR` / `R1A_UNKNOWN_OR_DUPLICATE_ACTOR` (fail closed on duplicates; test `s04.test.cjs:228`).
4. `People.active` must be strictly boolean `true` (`INACTIVE_ACTOR`). String `'TRUE'` is not truthy here (`s04/processor.js:31`).
5. Roles = `PersonRoles` rows with `person_id = person.id AND active === true`. **`People.role` is never a fallback** (`S04-implementation.md:9`, test `s04.test.cjs:96`). Empty → `NO_ACTIVE_ROLE`.
6. Actor object: `{id: People.id, email, roles[]}`. **All attribution (audit `initiating_actor`, `completed_by`, `updated_by`, TaskEvents.actor) uses `People.id`, not email** (`s04/processor.js:149,157`).
7. In G2 the actor is resolved twice: before the lock, and again under the lock (`:109,114`), so a role revoked during lock wait is honoured (test `s04.test.cjs:141`).

G1's `resolveActor` (`processor/actor.js:34-51`) trusts `command.actor_email`, uses `People.role` + non-schema `additionalRoles`, and ignores `PersonRoles`. Superseded — do not port.

Role vocabulary: G1 enum `Admin, Manager, Office, Finance, Store, Installer, Scaffolder, ReadOnly` (`types.js:68-77`). G3 additionally uses `Director` and `VariationApprover` (`adapter.js:27-28`); seed data has `Director` for Dan (`R/schema/config-seed.json` PersonRoles `PROLE-dan-director`).

### 2.2 Role predicates used by G3 (`adapter.js:26-29`, `operations-contract.js:34-35`)

- `admin` = Admin ∨ Manager
- `director` = admin ∨ Director
- `office` = director ∨ Office ∨ VariationApprover
- `officeManager` = admin ∨ Office
- `_r1cOffice` = Admin ∨ Manager ∨ Office

### 2.3 Job-level access rule ("assignment"), `adapter.js:37-44`

`_r1aAuthorizeJob(job_id)`:
- Job must exist (`R1A_JOB_NOT_FOUND`), `pilot_job === true` and `release_scope === 'R1'` (`R1A_OUTSIDE_PILOT`).
- Actor must be admin, OR own/back-up any Task on the job, OR be `responsible_person_id`/`office_owner_id` on any Issue of the job, OR be the job's `salesperson_id` — else `R1A_JOB_ACCESS_DENIED`.

### 2.5 Persisted PermissionRules (G2, `s04/processor.js:48-59`)

Table columns: `role, action, entity, scope, allowed` (`R/schema/tables.json`). Evaluation for COMPLETE_TASK:
- Candidate rules: `role ∈ actor.roles`, `action ∈ {'CompleteTask','*'}`, `entity ∈ {'Tasks','*'}`.
- Each candidate must have `scope ∈ {'All','Assigned'}` and boolean `allowed`, else `INVALID_PERMISSION_RULE` (fail closed on malformed config).
- A rule *applies* if scope is `All`, or the actor is the task's `owner_id`/`backup_id`.
- **Any applicable deny wins** (`PERMISSION_DENIED`); otherwise at least one applicable allow required.

Seed rules (`R/schema/config-seed.json`): Admin `*`/`*`/All allow; Office CompleteTask/Tasks/All; Director CompleteTask/Tasks/Assigned; Installer View/Jobs/Assigned; Scaffolder View/ScaffoldBookings/OwnCompany; Finance View/Reports/FinanceOnly.

**G3 does not consult PermissionRules at all** — its matrix is hard-coded in `adapter.js`. G1 uses a third, hard-coded `DEFAULT_PERMISSIONS` map (`processor/actor.js:6-32`) with different names (`Job` vs `Jobs`, `COMPLETE_TASK` vs `CompleteTask`; mismatch noted `S04-readiness.md:19`). See open question Q1.

Invariant tested in G1 that is worth preserving (`R/tests/processor.test.cjs:453-479`): **Admin bypasses role permission only — never ReleaseMode, pilot scope, version checks, locking, idempotency or audit.**

### 2.6 Signed identity (G2) — business intent vs plumbing

**Business intent (PRESERVE):** the initiating human must be authenticated by the platform, never asserted by an editable field; the service account that executes the write is *not* the actor; the authenticated identity is bound to the exact command so it can't be reused for another command or another user.

**Mechanics (PLATFORM PLUMBING — exists only because AppSheet "Call a script" runs as the app owner, `S04-readiness.md:43-47`):**
- Bridge web-app deployed `USER_ACCESSING` reads `Session.getActiveUser()`, requires it to equal `getEffectiveUser()` (`s04/bridge.js:13-15`), checks an allow-list (`:16`), and issues an HMAC-SHA256 proof.
- Proof fields (`s04/bridge.js:61-64`, verified `s04/identity.js:9-23`): `version:'S04-IDENTITY-2'`, `purpose:'S04_COMPLETE_TASK'`, `subject===email`, `jti` 16–120 chars, `audience='S04:<backendProjectId>:<sheetId>'`, `issued_at`, `expires_at` (issued with 120 s TTL; verifier allows ≤ 300 s lifetime, ≤ 30 s future skew, must be unexpired), `request_hash = sha256(canonical(request))`, `signature = HMAC(canonical(proof-without-signature), secret ≥ 32 chars)`, constant-time compare.
- Bridge also keeps a per-user pending command + rotating CSRF challenge (15 min) in UserProperties so an uncertain delivery retries the **same command_id** (`bridge.js:26-45, 52-59`).
- `jti` is validated for format but **no jti replay store exists**; exact proof replay is tolerated only because it collapses into idempotent command replay (test `s04-bridge.test.cjs:126`).

**G3 identity is weaker and different:** the AppSheet bot passes `actorEmail` as a *function argument* (from `USEREMAIL()`), and `_r1aDispatchBuiltRequest` overrides `options.actorEmail` with that argument (`request-row.js:378-385`). The only cross-check is that the request row's `submitted_by` (captured by AppSheet at row creation) equals it (`_r1aAssertSubmittedBy`, `request-row.js:136-140` → `R1A_ACTOR_MISMATCH`). Test name confirms: "useremail-only path works with blank active session" (`R/tests/appsheet-operations.test.cjs:85`). None of this should be ported.

**Supabase equivalent:** `auth.uid()`/JWT email → `people` row (unique index on `lower(trim(email))`, `active`) → `person_roles` (active). Resolve inside the RPC/transaction, never from the request body. HMAC proofs, challenges, bridge allow-lists, audience strings: drop entirely.

## 4. Idempotency

### G1 (`processor/command.js:18-36`)
Key `command_id`; storage an in-memory `Map` (no window, lost on restart). Same id + same caller-supplied `payload_hash` → returns the stored original result object; stats `commands_replayed++`. Same id + different hash → rejected, `error:'same command_id, different content'`, category **Validation** (not a dedicated conflict category). Runs *before* authentication. Only **committed** results are recorded (`processor.js:202`) — rejected commands are not remembered. Defects listed at `S04-readiness.md:35`.

### G2 (`s04/processor.js:117-141`) — the intended semantics
- Key: `command_id`. Storage: the `CommitJournal` row itself (`id = commit_id = 'S04-'+sha256(command_id)`), **no TTL/window — permanent**.
- Fingerprint: `sha256(canonical({request, actor:{id,email}}))` where `canonical` recursively sorts keys (`:10-14`). **Actor is part of the fingerprint** → cross-actor replay with the same id = conflict (test `s04.test.cjs:121`). Client `payload_hash` ignored (tests `:113,118`).
- More than one journal row for a command_id → `DUPLICATE_COMMAND_JOURNAL`.
- Same id, fingerprint/contract mismatch → `COMMAND_ID_CONFLICT`.
- Same id, `Committed` with saved result → return a clone of the saved result, **no writes**.
- Same id, `Prepared`/`Applying` → run recovery classification (see §6.1).
- Same id, any other state (`RecoveryRequired`) → `RECOVERY_REQUIRED`.
- Replay is still subject to *current* actor/permission/mode/pilot gates.
- Rejected commands write nothing and are therefore not deduplicated (they can simply be retried).

### G3 — three inconsistent conventions (flag for the port)
1. **Journal + fingerprint** (TASK_COMPLETE/REOPEN/EVIDENCE_ATTACH `services.js:339,412`; ISSUE_CREATE `:668`; SOLD_INTAKE `:1207`; BOOKING_INTAKE `:1301`; CONFIRM_BOOKING `:1563`; COMMISSIONING_RECORD `:1685`; all R1C commands `operations-contract.js:158-161`; materials `_matCommandStart`; S15 `:212-216`). Journal id `CJ-<NS>-<command_id>` (NS = R1A, R1C, MAT, S15…). Conflict → `R1A_COMMAND_CONFLICT` / `R1C_COMMAND_CONFLICT` / `MAT_REVIEW: conflicting command identity` / `S15_REVIEW: conflicting command replay`. Non-Committed prior → `*_RECOVERY_REQUIRED`.
   - Fingerprint content varies: TASK_COMPLETE uses `JSON.stringify(payload)` only — **no actor, no canonical key order** (`services.js:339`); R1C uses canonical `{request, actor: a.id}` (`operations-contract.js:158`); S15 compares `plan.kind` + full input.
2. **Deterministic-ID presence only, no payload comparison:** CALL_RECORD replays if `Calls['CALL-R1A-'+command_id]` exists (`services.js:618`); ISSUE_UPDATE replays if `AuditEvents['AE-R1A-'+command_id]` exists (`:625`). A changed payload under the same id silently returns "Replayed".
3. **Natural-state idempotency:** DEPOSIT_CONFIRM returns `AlreadyConfirmed`, OPERATIONAL_COMPLETE `AlreadyComplete`, CONFIRM_BOOKING `AlreadyBooked` (`command-result.js:272,303,308`); intake returns `duplicate:true` keyed on submission identity.

Replay return value in G3: `{status:'Replayed', …current rows…}` or the stored audit `after_json` + `{replay:true}` (`operations-contract.js:161`) — i.e. the **current** state or stored result with a replay flag, not always the byte-identical original result as in G2.

### Deterministic child IDs (a second idempotency layer — PRESERVE the idea)
Every row a command creates has an id derived from the command or the natural key, so a re-run collides instead of duplicating: `TE-<commit>`, `AE-<commit>` (`s04/processor.js:154-155`); `TE-R1A-<cmd>`, `AE-R1A-<cmd>`, `CALL-R1A-<cmd>`; `AUD-MAT-<cmd>-<type>-<id>-<action>`; `ORD-{jobId}-{merchantId}`, `MOV-{materialId}-v1`, `RES-{materialId}`, `IS-{jobId}-{stage}`, `SB-{jobId}`, `HO-{jobId}` (docs S07/S08/S09/S12/S13-implementation). In G2 an *orphan* deterministic event with no journal → `ORPHAN_EVENT_REQUIRES_REVIEW` (`:160`).

### Task dedupe (`processor/tasks.js:16-29`)
`instance_key = template_code-(jobId|'SYS')-(relatedType-relatedId|'ROOT')-(dueAt|'nodue')`. A new task is refused if a task with the same key exists whose status is not `Cancelled`/`Complete` (resilience variant also excludes `NotRequired`, `resilience/review.js:43`). So completing a task frees the key for re-creation. → Postgres partial unique index `ON tasks(instance_key) WHERE status NOT IN ('Complete','Cancelled','NotRequired')`.

### Outbox dedupe (`processor/outbox.js:15-24`)
`idempotency_key` unique among non-`Cancelled` items; schema marks it unique (`tables.json` Outbox). A cancelled item frees its key.

## 5. Audit

### What is recorded (schema `AuditEvents`, "Immutable audit log")
`id, entity_type, entity_id, action, before_json, after_json, initiating_actor, executing_service, timestamp, correlation_id, reason, commit_id, created_at`. No `updated_*`/`version` — append-only. The S04 sheet-store **forbids updates** to `TaskEvents`/`AuditEvents` (`s04/sheet-store.js:42`, test `s04-runtime.test.cjs:82`).

### Field semantics (consistent across generations)
- `initiating_actor` = the human's `People.id` (G2/G3) — distinct from `executing_service` (`'processor'`, `'S04-DEV'`, `'R1 AppSheet/S04'`, `'R1 AppSheet/S10'`, `'AppSheetOperations'`, `'ResilienceReview'`, module constants). **The human/service split must be preserved.**
- `correlation_id` = `command_id`. `commit_id` links the audit row, the mutated row(s) (`commit_id` column on every table), TaskEvents and the CommitJournal row.
- `reason` = free text from the command: completion note (`s04/processor.js:158`), `reason||note||review_notes` (`operations-contract.js:180`).
- `before_json` / `after_json`: full-row JSON snapshots. G2: exact task before/after (`:156`). G3 R1C: `before` = target row, **`after_json` = the command result object** (`operations-contract.js:180`) — and replay reads the result back *from the audit row* (`:161`). G3 TASK_COMPLETE: before = task, after = planned task.
- `action`: the command type or a domain verb (`'Complete'`, `'RecordCall'`, `'REASSIGN'`, `'ResolveMarkSucceeded'`, `'RaiseReviewTasks'`, `'FailureAlerts'`, `'WorkflowStage:Booked'`).

### When
- Exactly **one AuditEvent per committed command per primary entity**, written inside the commit, after the mutation and before the journal flips to Committed (G1 step 14; G2 `:181`; G3 `:180`). Multi-entity commands (S15 cancellation, materials) write one audit row per touched entity with id suffixing (`s15/cancellation.js:202`, `materials/workflow.js:135`).
- TaskEvents is a parallel immutable per-task history: `{task_id, action, old/new status, old/new owner, old/new due, reason, actor, timestamp, commit_id}` (`processor/tasks.js:92-111`).
- Audit insert is idempotent by id (`_r1sInsertAudit` returns early if the id exists, `services.js:7`).

### Failure auditing
- **Rejected commands are NOT audited anywhere.** G1 only increments `stats.commands_rejected`. G2: "Ordinary validation failures write nothing" (`S04-implementation.md:21,36`), asserted by `assertNoEffects` in every denial test. G3: the only trace of a failure is the `result_*` columns on the AppSheet request row (`command-result.js:397`) — platform plumbing.
- Mid-commit failure: journal row flipped to `RecoveryRequired` (G3 `operations-contract.js:181`, `services.js:488`); that *is* the durable failure record and feeds the review queue/alerts (§6.3).
- External-side-effect failures ARE audited: calendar service writes `<action>Failed` audit rows and one audit per attempt (`id 'AUD-CAL-'+outbox.id+'-'+action+'-'+attempt_count`, `calendar/service.js:182-186, 215`).
- Human resolutions of uncertain outcomes are audited with before/after of the Outbox row (`resilience/review.js:147`).

## 6. Journal / outbox / reconciler — the durable side-effect model

### 6.1 CommitJournal (write-ahead journal)

Schema: `id, commit_id (unique), state, command_id, entity_type, entity_id, expected_version, changes_json, prepared_at, committed_at, created_at`.

States (`types.js:29-34`): `Prepared → Applying → Committed`; `RecoveryRequired` reachable from any state (`journal.js:53-58`). Illegal transitions refused (`journal.js:35,45`; G2 `JOURNAL_TRANSITION_INVALID`). G3 mostly skips `Applying` (Prepared → Committed) except S15 (`s15/cancellation.js:191`).

G2 `changes_json` = the full **versioned plan** `S04-1` (`s04/processor.js:163-164`): validated request, actor, canonical request string + hash, exact `before`/`after` row images, the planned TaskEvent and AuditEvent rows (with deterministic ids), `intended_result`, `result` (null until committed), `recovery_classification`. Result and terminal state are saved in **one row write** (`:183`). Size cap 45 000 chars → `JOURNAL_TOO_LARGE` (Sheets cell limit — plumbing).

Recovery classification on retry of the same command (`s04/processor.js:91-100, 128-141`; table at `S04-implementation.md:44-51`):
| Observed | Action |
|---|---|
| no journal row | process normally |
| Committed + result | replay, no writes |
| `NOT_APPLIED` (task equals `before` exactly AND neither event exists) | re-check gates/version, reuse same plan + ids, complete |
| `FULLY_APPLIED` (task equals `after` exactly AND both events equal plan exactly) | finalise journal/result; never re-apply |
| `PARTIALLY_APPLIED` / any mismatch | persist `RecoveryRequired`, refuse; manual investigation |
| already `RecoveryRequired` | refuse |

Plus the **entity quarantine rule**: any non-Committed journal row for a *different* command on the same entity blocks new commands on that entity with `RECOVERY_REQUIRED` (`:143`). G3 R1C is broader: any non-Committed `CJ-R1C-*` row blocks *all* R1C commands (`operations-contract.js:162`); S15 blocks per job (`s15/cancellation.js:219`).

Tested at all six write checkpoints (`s04.test.cjs:157-170`): interruptions after writes 1–2 → NOT_APPLIED → retry commits; after 3–4 → RecoveryRequired; after 5 → FULLY_APPLIED → finalise; 6 → already committed. Response to the client during an interruption is `status:'Pending', error:'INTERRUPTED_RETRY_SAME_COMMAND'` (`:186-187`) — "must not be presented as proof that no write happened" (`S04-implementation.md:42`).

G3 R1C adds a useful pattern: **validate and run the service against a buffered in-memory copy first, journal, then flush** (`operations-contract.js:143-150,165-181`), so a late validation failure produces zero writes (test `appsheet-operations.test.cjs:37,44`).

G1 reconciler (`processor/reconciler.js:10-52`) only *suggests* actions (`discard` / `commit` / `manual_review`); field-level comparison ignoring `_`-prefixed keys.

**CLASSIFICATION: the entire Prepared/Applying/recovery-classification machine exists because Google Sheets has no multi-row atomic transaction** (`S04-implementation.md:55`: "Storage is not an atomic multi-table transaction"). In Postgres one transaction makes `NOT_APPLIED` vs `PARTIALLY_APPLIED` impossible. What survives is: (a) a durable **commands/idempotency table** holding `command_id`, fingerprint, actor, entity, expected_version, stored result, status; (b) `commit_id` correlation across all rows touched. `RecoveryRequired`, the 15-minute "stuck commit" alert, the entity quarantine rule and `RS-RECOVERY` tasks become unnecessary for DB writes (they remain relevant only for external side effects — see outbox).

### 6.2 Outbox

Schema: `id, idempotency_key (unique), action_type, target, payload_hash, job_revision, attempt_count, next_attempt, external_id, response_summary, correlation_id, status, created_at, commit_id`. (The schema has **no payload column**; G1's in-memory item carries `payload`, `outbox.js:32`. Real producers store the payload on a domain row — `CalendarLinks`, `Communications.outbox_id` — and the outbox row references it.)

Statuses (`types.js:36-43`): `Pending, Processing, Succeeded, RetryDue, NeedsReview, Cancelled`.

Lifecycle rules (G1 `outbox.js:57-105`, hardened in `calendar/service.js`):
- Only `Pending`/`RetryDue` may go to `Processing`; `attempt_count++` at that moment (`:60-64`).
- **Mark `Processing` BEFORE the external call** so a crash is visible as an uncertain row (`calendar/service.js:254-256`; Xero same, `RESILIENCE-implementation.md:19`).
- Success → `Succeeded` + **persist `external_id`** + `response_summary`.
- Transient failure → `RetryDue` with `next_attempt`; at `attempt_count >= 5` → `NeedsReview` with "Max retries exceeded. Last error: …" (`outbox.js:80-84`). Calendar: `CAL_MAX_ATTEMPTS=5`, backoff minutes `[1,2,4,8,16]` (`calendar/service.js:23-24`). Upload retry: same 5 / `[1,2,4,8,16]` (`upload-retry.js:24-25`). Xero: **3 attempts max** (`RESILIENCE-implementation.md:19`). G1 generic backoff: `min(1000·2^attempt, 300 000) + rand(0..1000)` ms (`outbox.js:117-123`).
- **Uncertain outcome (timeout / no confirmation / response without an id) → `NeedsReview`, never blind retry** (`outbox.js:91-97`; `calendar/service.js:269,289,293` `UNCERTAIN_OUTCOME`; `xero/adapter.js:83`). Spec quote in `resilience/review.js:2`: "a timeout after an external send is an uncertain outcome … raise a review task instead of blindly resending".
- Before re-creating after an uncertain prior attempt, **reconcile by searching the external system for a tag** carrying the idempotency key; multiple matches → `DUPLICATE_EVENTS` review (`calendar/service.js:275-284`).
- Stalled `Processing` > 15 min → flipped to `RetryDue` with summary `STALLED: … reconcile before retry` and audited (`calendar/service.js:302-315`, `CAL_STALLED_MINUTES=15`); upload retry uses 10 min (`upload-retry.js:26`).
- Permanent/config refusals (`CAL_REFUSED`, target mismatch, missing link) → `NeedsReview` immediately, no retry.
- `job_revision` on the row: confirmations/acknowledgements of an older revision cannot satisfy the current one (`release-plan.md:45`).
- Dispatch itself is gated by ReleaseMode (FN-02/FN-09 Automated/Pilot) **and** a second environment switch (`calendarMode`/`xeroMode === 'LIVE'`, default CAPTURE = rows stay Pending, nothing sent) **and** allow-lists of recipients/calendars (`calendar/service.js:10-16`; `apps-script/OutboundGuard.js:14-33`). A transport response "proves only submission. Receipt needs separate human evidence" (`OutboundGuard.js:38`).

G1 `reconcileOutbox` (`reconciler.js:54-69`): for `NeedsReview` items with an `external_id`, ask an injected checker; `SUCCEEDED` → suggest mark_succeeded, `FAILED` → suggest mark_failed. Suggestions only.

### 6.3 Review queue, review tasks, failure alerts (`R/resilience/review.js`, FN-14)

- `_rsReviewQueue` (read-only, `:58-80`) unifies: Outbox `NeedsReview`/`RetryDue`/`Processing` stalled ≥ 15 min (age from `created_at`); Communications `Uncertain`/`Failed`; CommitJournal `RecoveryRequired` or non-Committed for ≥ 15 min. Each item: kind, id, action_type, status, attempts, target, summary, external_id, age_minutes, job_id, `owner_service` (Calendar rows → `CalendarService`, else `ResilienceReview`), `suggested` action text. Sorted oldest first. Indicators: `pending_outbox` count, `oldest_pending_outbox_at/minutes`, `last_health_check_at`, `last_health_success_at`.
- `_rsRaiseReviewTasks` (`:84-98`): one open task per uncertain item; template `RS-RECOVERY` for journal items else `RS-REVIEW`; `instance_key = <code>-<kind>-<id>`; **`RetryDue` items are skipped** (automatic retry still pending); owner = active Office person whose display_name contains "tanya" (else first Office), backup = active Admin/Manager containing "ben" (`:32-38`); priority 1, due now; one batch audit row if any created. Requires `actor` + `command_id`.
- `_rsFailureAlerts` (`:102-127`): one `RS-ALERT` task **per component per calendar day** (`instance_key = 'RS-ALERT-'+component+'-'+YYYY-MM-DD`, day taken from the UTC ISO string). Sources: injected S16 health `issues` (Critical) and heartbeat warnings in state Failing/Stale; any `Processing:*` heartbeat whose latest outcome ≠ OK with no success within `stale_minutes` (default 120) → Critical; any `RecoveryRequired` commit → Critical `CommitJournal`; Outbox `NeedsReview` with attempts ≥ 5 → Warning `Outbox`. Always returns the manual fallback text: if automation itself stops, Tanya runs SYS01 manually, Ben backup (`:126`).
- `_rsResolveOutbox` (`:131-149`): human decision `MarkSucceeded | Cancel | Retry`; requires actor, command_id, outbox_id, **reason**; `MarkSucceeded` **requires `external_id`** ("confirm the external result first"); `Retry` → `Pending` with `next_attempt:null`; only `NeedsReview/RetryDue/Processing` rows are reviewable; Calendar rows refused (owned by the calendar service); completes the matching `RS-REVIEW-Outbox-<id>` task; audited with before/after; idempotent by deterministic audit id → `{replay:true}`.
- All three mutators require FN-14 = Automated/Pilot/R1 (`:27-31`). `runRsSweep` is designed for a 30-minute schedule (`cloud-adapter.js:21-22`).

Health (`processor/health.js:9-24`, `s16/heartbeat.js`): one check per integration; `last_success` carried forward on failure; heartbeat staleness default 120 min (`heartbeat.js:12`, setting `health.heartbeat_stale_minutes`, valid 0 < v ≤ 10080) and **only alarmed inside the staffed window** (`office.staffed_weekdays`, Europe/London) — outside it the state is `Quiet` not `Stale` (`:196-198`).

## 7. Locking / concurrency model

- G1: per-entity in-memory lock with 30 s expiry; busy → immediate reject `Concurrency` / `'lock held by <owner>'` (`processor/locking.js:24-49`, `processor.js:136`). Defect: entity is read **before** the lock (`processor.js:121` vs `:136`; `S04-readiness.md:24`).
- G2: **one global script lock** (`LockService.getScriptLock().tryLock(5000)`, `s04/runtime.js:24-27`) → `LOCK_BUSY` on timeout. Everything that matters (actor roles, task row, mode rows, job row, journal lookup) is **re-read after acquiring the lock** (`s04/processor.js:112-121`). Tests: overlapping command locked out, same-version loser gets `STALE_VERSION` (`s04.test.cjs:125-141`).
- G3: `store.withLock(fn)` = `getScriptLock().waitLock(30000)` (`r1-appsheet/cloud-adapter.js:4`), 5 s in resilience (`resilience/cloud-adapter.js:14`).
- Stated limitation: "ScriptLock serialises calls within that project, not human spreadsheet edits or another project… One standalone S04 project must be the only operational writer" (`S04-implementation.md:55`).

**Invariants protected:**
1. check-then-act atomicity of {idempotency lookup → version compare → mutation → version bump → audit → journal} for a command;
2. at most one winner among concurrent commands carrying the same `expected_version` on one entity (loser sees stale);
3. at most one execution per `command_id` under concurrent duplicate submission;
4. authorization evaluated against state that cannot change before the write (roles/mode re-read under lock);
5. single-writer: only the processor mutates authoritative tables (AppSheet is "never authoritative", `adapter.js:1`).

**Postgres translation:** one transaction per command inside an RPC (`SECURITY DEFINER` function or server-side route using a service connection):
`INSERT INTO commands(command_id, …) ON CONFLICT (command_id) DO NOTHING` → if conflict, `SELECT … FOR UPDATE` the existing row and compare fingerprint (replay/conflict); resolve actor + roles + release mode in the same transaction; `SELECT … FOR UPDATE` the target entity row; compare `version`; mutate with `version = version + 1` (or `UPDATE … WHERE id=$1 AND version=$2` and check rowcount); insert audit/task-events; store result on the command row; commit. The global lock becomes unnecessary — row locks give per-entity serialisation, the unique constraint gives per-command serialisation. Invariant 5 → RLS that denies direct INSERT/UPDATE/DELETE on authoritative tables to `authenticated`, with writes only through RPCs.

## 9. Clock / timezone / determinism

- **Business timezone is Europe/London, "not the workstation's timezone"** (`R/config/README.md:9`; `config/environment.example.json` `"timezone":"Europe/London"`; `OutboundGuard.js:16` refuses any other). Staffed weekdays default Mon–Fri `[1..5]`; `holidayDates:null` means "not supplied", not "no holidays"; `capacitySettings:null` = unknown.
- Date-only business values are `YYYY-MM-DD` strings derived in Europe/London (`s10/operations.js:20-32` `_s10LocalDate`, `s16/health.js:24-25`, planner default `adapter.js:235`, staff-facing dates `command-result.js:196-199`). Invalid calendar dates are rejected by round-tripping through `Date.UTC`.
- Timestamps are UTC ISO-8601 strings everywhere (`new Date().toISOString()`).
- **Inconsistency:** G1 `clock.js:9-12,22` `todayDate()` slices the **UTC** ISO string, and `resilience/review.js:106` derives the alert "day" the same way — wrong around midnight during BST. Port with Europe/London.
- Clock injection: G1 `testClock` with `advance/advanceDays/setTo` (`clock.js:16-28`); G2 injects `options.now` (`s04/runtime.js:26`); stage modules accept `input.at` (validated ISO) as the command's "now" (`materials/workflow.js:54`, `resilience/review.js:23`). G1 is only partially clock-driven: `recordAudit`, journal, outbox and `recordTaskEvent` call `new Date()` directly (`audit.js:19`, `journal.js:24`, `outbox.js:35`, `tasks.js:105`).
- **Determinism as actually implemented** (the literal phrase "deterministic business effects" does not occur anywhere in the repo — grep found nothing): (a) one `now` captured once per command and used for every row that command writes (`s04/processor.js:147-159`, `operations-contract.js:165`); (b) ids of all derived rows are pure functions of `command_id`/natural keys (§4), so re-execution yields byte-identical rows — required by G2's exact-equality recovery classification (`:90-99`); (c) canonical JSON (sorted keys) for hashing; (d) task `instance_key` and outbox `idempotency_key` deterministic; (e) no randomness in G2/G3 ids (G1 uses `Math.random()` ids — do not port). No PROD test-clock bypass is permitted (`config/README.md:7`).

## 10. Error codes and result shapes

### G1 result (`processor.js:56-67`)
`{command_id, accepted, committed, commit_id, tasks_created[], outbox_items[], audit_events[], error, error_category, mode}`. `FailureCategory` (`types.js:79-89`): Validation, Permission, Concurrency, DisabledMode, PilotScope, Transient, Authentication, Uncertain, Fatal. (Transient/Uncertain are never produced by the processor itself.)

### G2 result
Success (`s04/processor.js:161-162`): `{status:'Committed', accepted:true, committed:true, command_id, task_id, version, commit_id, task_event_id, audit_event_id}`.
Failure (`:186-187`): `{status:'Failed'|'Pending', accepted:false, committed:false, error:<CODE>}` — `Pending` iff persistence had started (`INTERRUPTED_RETRY_SAME_COMMAND`); otherwise `Failed` (`PROCESSOR_ERROR` default).
Codes: DEV_ONLY, SHEET_ID_MISMATCH, PROJECT_ID_MISMATCH (plumbing); INVALID_FIELDS, INVALID_COMMAND_ID, INVALID_TASK_ID, ACTION_DENIED, INVALID_VERSION, INVALID_PAYLOAD; TRUSTED_IDENTITY_REQUIRED, UNKNOWN_OR_DUPLICATE_ACTOR, INACTIVE_ACTOR, NO_ACTIVE_ROLE; LOCK_BUSY; TASK_NOT_FOUND, PERMISSION_DENIED, INVALID_PERMISSION_RULE; MODE_MISSING_OR_DUPLICATE, MODE_DENIED, PILOT_SCOPE_DENIED, JOB_NOT_FOUND, OUTSIDE_PILOT, SYNTHETIC_SCOPE_REQUIRED; DUPLICATE_COMMAND_JOURNAL, COMMAND_ID_CONFLICT, RECOVERY_REQUIRED, ORPHAN_EVENT_REQUIRES_REVIEW; STALE_VERSION, TASK_STATE_DENIED, TASK_BLOCKED, TASK_DEPENDENCY_UNSATISFIED; JOURNAL_TOO_LARGE, JOURNAL_TRANSITION_INVALID. Transport: S04_TRANSPORT_REFUSED, S04_RUNTIME_REFUSED, BACKEND_UNCONFIRMED, DELIVERY_UNCERTAIN_RETRY_SAME_COMMAND, BRIDGE_* / CHALLENGE_* (plumbing).

Client state machine (`s04/client-state.js`): `Idle → Pending → Committed | Failed`; **a task may be hidden only when** `status==='Committed' && committed===true && command_id/task_id match && version===expected+1 && commit_id non-empty` (`:16-19,31`); anything unverifiable stays `Pending` and `retry()` re-sends the **identical stored request**; double-tap guarded (`SUBMISSION_IN_PROGRESS`), one command per controller (`COMMAND_ALREADY_EXISTS`). This "pending until verified, retry same id" contract is business UX worth preserving.

### G3 result
Transport: `{ok:true, command_type, actor_id, result}` / `{ok:false, error}` + additive `feedback:{status, heading, message, code}` (`command-result.js:371-378`).
Codes are namespaced: `R1A_*` (office adapter/services), `R1C_*` (operations contract), `R1U_*` (upload retry), and stage modules throw `"<NS>_<CLASS>: detail"` strings with classes `_REFUSED`, `_REVIEW`, `_STALE`, `_CONFIG`, `_RECOVERY_REQUIRED`, `_DATE_INVALID` (`command-result.js:207-211` parser).

Staff-facing vocabulary (`command-result.js:14-16`) — **a good business-level result model to port**:
| Status | Heading | Meaning |
|---|---|---|
| Succeeded | SUCCESS | committed |
| FollowUpRequired | SAVED – FOLLOW-UP NEEDED | committed, but leaves an owned follow-up (e.g. task moved to Waiting with a `blocking_reason`) |
| ActionRequired | ACTION REQUIRED | nothing written; user can fix and resubmit (missing field, stale version, stage not eligible) |
| Failed | COULD NOT COMPLETE | nothing written; user cannot fix (permission, mode off, not in pilot, config, recovery, id conflict); message appended with `Reference: <command_id>` (`:396`) |
| UploadPending | UPLOAD PROCESSING | plumbing only |

Classification rules by code pattern (`:213-236`): `*_REQUIRED_<FIELD>` → ActionRequired with a field label; `STALE` → ActionRequired; `RECOVERY_REQUIRED` → Failed; `_MODE_DENIED|_MODE_MISSING` → Failed "switched off"; `_DENIED` → Failed permission; config/schema → Failed; `_CONFLICT` → Failed; `R1x_INVALID_*` → ActionRequired; `Sxx_REVIEW` → ActionRequired; `Sxx_REFUSED` → Failed; `_NOT_FOUND` → Failed; default Failed. Full per-code message table at `:42-167`; per-command success messages at `:246-327`; result extras (`result_job_id`, `result_job_id_human`, `result_version`, `result_workflow_stage`, `result_issue_id`, `result_stage_id`) at `:329-340`. Principle (`:3-4`): **transport success ≠ business success** — the outcome is always parsed from the command response. Final outcomes (Succeeded/FollowUpRequired) are never overwritten (`:394`).

## 12. Open questions / ambiguities

1. **Which authorization source is authoritative?** Three exist: G1 `DEFAULT_PERMISSIONS` (hard-coded, stale names), G2 persisted `PermissionRules` with deny-precedence (only wired for CompleteTask), G3 hard-coded role predicates in `adapter.js` (ignores PermissionRules entirely). Seed PermissionRules cover only 6 rules. Recommend porting the G3 matrix as code and treating PermissionRules as optional; needs a decision.
2. **Role list drift:** `ActorRole` enum lacks `Director` and `VariationApprover`, both used by G3 and (Director) seeded. `ReadOnly` and `Finance` have no command permissions anywhere.
3. **Idempotency fingerprint scope in G3 is inconsistent** (payload-only vs request+actor vs presence-only for CALL_RECORD/ISSUE_UPDATE). G2 semantics (request + actor, conflict on any change) appear to be the intent (`S04-readiness.md:35`), but G3 TASK_COMPLETE allows a *different actor* to replay the same id + payload. Confirm G2 semantics for the port.
4. **Replay return value:** G2 returns the exact stored original result; G3 returns current row state + `status:'Replayed'`. Pick one (recommend stored result + `replay:true`).
5. **Are rejected commands to be recorded?** Currently never (zero-write rule), so there is no audit trail of denied attempts (permission failures, stale versions). The spec intent is not visible in code. In Postgres a rejected-command log outside the rolled-back transaction is cheap — needs a product decision.
6. **`release_scope` is single-valued per job**, and R1 commands require `'R1'` while R2 commands require `'R2'` and R3 commands require only `pilot_job` (`operations-contract.js:37,44`). As coded a job cannot be operated by both R1 office commands and R2 goods-in. Presumably an artefact of per-stage synthetic fixtures; the intended production meaning (cumulative? per-function scope?) is unspecified. `authorised_job_scope='All'` is also rejected everywhere today, so there is no coded path for post-pilot expansion.
7. **G1 treats `Manual` as "reject" while G3 requires `Manual` for human-decision commands.** G3 is clearly the later intent, but there is no code path describing what a *Manual-mode Automated-target function* (e.g. FN-02 Calendar in R1: planned_R1_mode Manual) should do at command time beyond "create an owned manual task" (`release-plan.md:45`). The task-creation-instead-of-outbox branch is implemented ad hoc per stage, not in the core.
8. **Outbox payload storage:** the persisted schema has no payload column, only `payload_hash`; where the send payload lives differs per producer (CalendarLinks, Communications). A generic worker needs a defined contract.
9. **`jti` replay protection is not implemented** (format check only). Irrelevant once Supabase auth replaces proofs, noted for completeness.
10. **Timezone of "per day" alert keys and G1 `todayDate()` is UTC**, contradicting the Europe/London rule. Assumed bug.
11. **Retry limits differ** (5 for calendar/upload, 3 for Xero, generic backoff in ms vs minute table). No single documented policy; `RESILIENCE-implementation.md:19` is the only source for "3 attempts".
12. **G1 error-category quirk:** Manual mode rejections are labelled `PilotScope` (`processor.js:129-130`); same-id-different-payload is labelled `Validation`. Do not replicate; use dedicated `ModeDenied` / `CommandConflict` codes.
13. **Health/heartbeat ownership:** `recordHealthCheck` is imported but never called by the G1 processor (`processor.js:14`); HEALTH_CHECK and RECONCILE command types have no handler anywhere in G3. Health is driven by S16/resilience scheduled functions instead.
14. **S04-manual-setup.md (176 lines)** and the AppSheet security-filter guidance (`S04-readiness.md:27`) were not analysed in depth — entirely platform configuration; the *row-visibility rules* they describe (own People row, own active roles, tasks by owner/backup, installer jobs via active allocations, scaffolder by own company, finance/private issues excluded, files protected separately) should be cross-checked by whoever designs RLS.
